## 1. Method and honest claim boundary

`validate_kql.ps1` is a **deterministic, offline, static** validator. It reads text and
hashes; it does **not** execute KQL.

> **KQL backend execution was NOT performed.** No local KQL parser, Sentinel backend or
> query engine exists in this environment, so the queries were neither parsed nor run by
> any KQL engine. Syntax was checked only by the static, text-based checks listed below.
> Nothing here is a live-Sentinel validation and nothing here is a production claim.

The validator distinguishes **query logic** from **comments**: `//`-prefixed lines are
stripped before the "absent from logic" checks, so the query comments cannot mask or fake
a result. For the strongest tokens (`FromBase64String`, `BASE-01`, `4104`, `DET-003`) the
check is run against the **whole file including comments**, so those tokens do not appear
anywhere in the primary query at all.

## 4. Limitations

- **No KQL engine was involved.** The queries were not parsed, converted or executed;
  syntax and runtime behaviour are unverified beyond the static text checks. There is no
  local KQL parser.
- **The source schema is an assumption.** The `Event` table, the `Source` /
  `EventLog` values and the dynamic (`JSON`) `EventData` shape were assumed, not verified
  against a live Sentinel workspace. A workspace using the `ParameterXml` shape needs the
  alternative projection documented in `KQL_NOTES.md` §1.
- **The two query forms are not equivalent to each other**, by design. The portable file
  matches only the long switch; the regex file matches the original token-exact short
  switches. This difference is documented, not hidden (`KQL_NOTES.md` §5).
- **The regex file inherits the original detector's Image behaviour** (the standard
  `endswith` idiom from the Phase 9 Sigma rule), which is narrower than the original
  unanchored `(powershell|pwsh)\.exe` substring match; the difference is documented.
- **No coverage or performance claim.** Static validation says the artifact is
  structurally faithful; it says nothing about detection rates or false-positive rates in
  any environment.
- The measured lab false-positive history (38 of 39 hits were the operator's own WinRM
  administration) is context for the deploying team, not a tuning that was applied here.
